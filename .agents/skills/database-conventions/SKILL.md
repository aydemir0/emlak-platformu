# Database Conventions

## Design from invariants

Before defining a table or query:

1. Identify the owning domain and authoritative source.
2. Write the invariants, lifecycle states, cardinality, and deletion behavior in plain language.
3. Identify actors and access rules, including service roles and background jobs.
4. Estimate read/write patterns and expected scale using current evidence.
5. Decide transaction, concurrency, audit, privacy, and retention needs.
6. Apply `security-rules`; apply `project-architecture` for cross-domain ownership.

Do not write a migration until requirements and ownership are clear. Do not use the database as an untyped JSON store for known relational data.

## Naming and types

- Use lowercase `snake_case` for schemas, tables, columns, constraints, indexes, functions, and enums.
- Use plural table names and singular foreign-key stems: `properties`, `property_id`.
- Prefer UUID primary keys generated by a documented server/database strategy.
- Use `timestamptz` for instants and store them in UTC. Use `date` only for calendar dates and `time` only with explicit timezone semantics.
- Use integer minor units plus currency code for money when exact arithmetic and currency boundaries matter; never use floating point for money.
- Use numeric/decimal only with deliberate precision and scale.
- Use `text` plus checks when values evolve frequently; use PostgreSQL enums only when the migration coupling is acceptable.
- Use arrays or `jsonb` only for genuinely aggregate or schemaless attributes. Promote queried, constrained, related, or independently updated values to columns/tables.
- Store normalized values separately from display values when both are needed.
- Avoid reserved words, opaque abbreviations, and boolean names without positive meaning.

## Required record metadata

Business tables should normally include:

- `id`;
- `created_at` and `updated_at`;
- `deleted_at` for soft-deletable records;
- actor/provenance fields when accountability requires them;
- a version or equivalent concurrency field when conflicting edits matter.

Do not add metadata mechanically when the table is immutable, derived, or a pure junction. Document exceptions.

## Enforce integrity in PostgreSQL

- Mark required data `not null`.
- Use foreign keys with explicit update/delete behavior.
- Add unique constraints for business identities and idempotency keys.
- Use check constraints for ranges, mutually dependent fields, valid time windows, and state-dependent invariants that can be expressed safely.
- Use exclusion constraints for scheduling overlap when appropriate.
- Prefer database defaults for immutable creation timestamps and safe constants, not for hidden business decisions.
- Do not rely only on TypeScript or UI validation for data integrity.
- Do not use cascading delete on business records without a documented, reviewed lifecycle.

For soft-deleted data, use partial unique indexes where an identifier may be reused only after deletion. Decide whether foreign keys may reference deleted parents and enforce the behavior in application transitions.

## Model relationships explicitly

- Use junction tables for many-to-many relationships such as property features.
- Give junction tables their own identifier only when other records reference the relationship or it has a lifecycle; otherwise use a composite key.
- Keep properties, property media, advisors, leads, customers, customer requests, and appointments distinct.
- Model locations as a stable hierarchy or graph with explicit level/type and parent invariants; do not infer hierarchy from display strings.
- Keep SEO landing pages separate from arbitrary filter state and link them to a curated query definition.
- Separate operational records from append-only analytics/audit events.

## Apply soft deletion

- Use `deleted_at is null` as the default active-record predicate.
- Record who deleted/restored and why when the action is sensitive.
- Make delete and restore operations application use cases, not ad hoc row updates.
- Define whether child records hide, detach, remain accessible, or cascade into their own soft-delete transition.
- Ensure uniqueness, indexes, RLS, admin queries, analytics, and exports handle deleted rows deliberately.
- Define retention and eventual hard deletion for PII and media; soft delete is not a substitute for privacy erasure.
- Never silently resurrect stale relationships during restore.

## Design indexes from queries

- Start with primary, unique, foreign-key, common filter, join, and order requirements.
- Match composite index column order to equality, range, and ordering behavior of real queries.
- Use partial indexes for active/published subsets when selective.
- Use GIN/GiST only for demonstrated full-text, JSON, array, spatial, or exclusion needs.
- Avoid redundant indexes and indexing low-selectivity columns alone without evidence.
- Review write amplification and storage cost.
- Validate important queries with representative data and execution plans before optimization claims.

SEO/filter designs must not create an index for every theoretical combination. Curate supported filters and measure actual query patterns.

## Transactions and concurrency

- Group state changes that must succeed or fail together in one transaction.
- Lock the narrowest rows necessary for transitions, ordering, allocation, or overlap checks.
- Use optimistic concurrency for human edits when overwrites must be detected.
- Use unique constraints as the final guard against duplicate submissions and idempotency races.
- Keep external network calls outside open database transactions.
- Use an outbox or reconciliation pattern when a committed change must reliably trigger email, analytics, search, or media work.
- Document isolation assumptions for appointment booking, property publication, assignment, and media ordering.

## Supabase and RLS

- Enable RLS on every client-accessible table and deny by default.
- Write policies around authenticated identity and explicit membership/ownership relationships.
- Separate read, insert, update, and delete policies when their rules differ.
- Keep service-role credentials server-only and use them only in tightly scoped trusted code.
- Do not treat RLS as the sole authorization layer; application use cases must enforce business permissions too.
- Prevent user-controlled columns from changing ownership, tenant, role, publication, or audit fields.
- Test policies for anonymous, ordinary, advisor, admin, cross-account, deleted, and malformed cases.
- Use security-definer functions sparingly, set a safe search path, minimize privileges, and review them as security-sensitive code.

## Migrations

When implementation begins:

- make migrations deterministic, ordered, reviewed, and safe to rerun only where explicitly designed;
- use expand/migrate/contract for breaking production changes;
- avoid long table locks and unbounded backfills in deploy-time migrations;
- add nullable/new structures first, backfill in bounded observable batches, validate, then tighten constraints;
- provide rollback or forward-fix instructions based on data-loss risk;
- never edit an applied production migration to change history;
- regenerate database types after schema changes and review the diff;
- include RLS, grants, constraints, indexes, comments, and data migration behavior in review.

Do not create migrations during the current governance-only phase.

## Audit and analytics data

- Keep audit logs append-only to normal application roles.
- Record actor, action, target type/id, timestamp, correlation/request ID, outcome, and safe before/after detail where justified.
- Never store secrets, tokens, passwords, full payment details, or unnecessary PII in audit/analytics payloads.
- Define retention and access for audit and analytics separately from operational tables.
- Use a versioned event name and schema for internal analytics.
- Do not allow analytics delivery failure to roll back the authoritative transaction.

## Review checklist

- Are ownership, invariants, lifecycle, and deletion behavior documented?
- Do constraints protect required relationships and business uniqueness?
- Are soft-delete, restore, retention, and privacy erasure coherent?
- Are query-driven indexes sufficient without speculative combinations?
- Are transaction, locking, concurrency, and idempotency rules explicit?
- Is RLS deny-by-default and backed by application authorization?
- Are migrations deploy-safe and generated types kept current?
- Are audit and analytics records useful without leaking sensitive data?
